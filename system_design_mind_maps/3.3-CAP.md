# CAP Theorem for Distributed Data Stores

> Based on: Brewer’s conjecture, Gilbert & Lynch’s formal proof, and Henry Robinson’s CAP FAQ.

---

## 1. Core CAP Statement

The **CAP theorem** (Brewer’s conjecture, proved by Gilbert & Lynch in 2002) describes a limitation of distributed read/write storage systems in the presence of network partitions:

> In an asynchronous network where messages can be lost (i.e., network partitions can occur), it is impossible to implement a read/write register that is simultaneously:
>
> 1. **Atomic (linearizable)**  
> 2. **Available**  
> 3. **Partition tolerant**.

If partitions are possible, you cannot guarantee both **C** and **A** at the same time for all requests.

---

## 2. Model and Definitions

Following Gilbert–Lynch and Henry Robinson’s CAP FAQ.

### 2.1 Read–Write Register

- Conceptual **register** with two operations:
  - `set(X)` — write value `X`.
  - `get()` — read the current value.
- A key–value store can be viewed as a set of such registers, one per key.

### 2.2 Atomic Consistency (C)

- CAP’s **Consistency** is **atomicity / linearizability**.
- Informally:
  - Operations appear as if they execute on a single machine.
  - There exists a **single global order** of operations that:
    - Respects real-time ordering (if a write completes before a read starts, the read must see that write).
    - Produces results identical to those of a correct single-node implementation.

This is stronger than eventual consistency; it’s the strongest commonly used consistency model.

### 2.3 Availability (A)

- Every request to a non-failed node must eventually receive a **successful, correct response**.
- “Successful” means:
  - The operation returns a value (not an error or infinite wait).
  - The returned value is valid for some correct execution (e.g., a read returning some previously written value).

### 2.4 Partition Tolerance (P)

- The system continues to operate despite **arbitrary message loss** between nodes.
- A **network partition** is modeled as a pattern of message loss that permanently separates groups of nodes (no messages cross between them).

Partition tolerance is not a “feature toggle”; in most real systems, network partitions are possible events you must design for.

---

## 3. Why C, A, and P Cannot All Hold

High-level proof sketch (after Gilbert & Lynch, as explained in the CAP FAQ):

1. Assume a distributed register is **atomic**, **available**, and **partition tolerant**.
2. Consider a partition that splits the system into two groups of nodes, `G1` and `G2`, such that no messages traverse the cut.
3. A client sends `set(X)` to some node in `G2`. Since nodes must be available, `G2` processes this write.
4. Another client sends `get()` to some node in `G1`. Since nodes must be available, `G1` must respond.
5. For **atomic consistency**, the read in `G1` must reflect the write of `X` in `G2`.
6. But there is no way for `G1` to learn about `X`, because messages from `G2` are dropped by the partition.
7. `G1` has two options:
   - Return the **old value** (violating atomic consistency), or
   - Refuse/block the request (violating availability).

Therefore, under possible partitions, you cannot guarantee both **C and A** for all operations.

---

## 4. Misconception: “Pick Any Two”

The popular CAP triangle is easy to misread as:

> “You can pick any two of C, A, and P.”

This is misleading:

- In any realistically distributed system, **partitions can occur** (link failures, switch reboots, routing bugs).
- You cannot simply “choose not to have P” — partition tolerance is a **property of the environment**, not a design option.
- A better reading is:
  - **If partitions are possible, you cannot provide both C and A for all requests.**

Systems that are “CA” (consistent and available but not partition tolerant) are essentially **single-node or single-site systems** where partitions are ruled out by assumption.

## 5. CP vs AP Systems

Given that P is forced on you in a real distributed system, the practical choice under partition is which property to weaken: C or A.

### 5.1 CP (Consistent + Partition Tolerant)

- Prioritize **Consistency** over Availability during partitions.
- Behavior under partition:
  - Some nodes (often those in the minority partition) will refuse or block operations to avoid serving stale or conflicting data.
- Properties:
  - Reads and writes that complete are linearizable.
  - Requests to isolated or minority nodes may fail or time out.

Examples (categories, not specific vendor endorsements):

- Strongly consistent distributed stores using leader-based replication and majority write/read quorums.
- Coordination/config services (e.g., ZooKeeper/etcd/Consul style) that prefer safety and will block if they cannot reach a quorum.

### 5.2 AP (Available + Partition Tolerant)

- Prioritize **Availability** during partitions.
- Behavior under partition:
  - Each partition continues to accept reads/writes locally.
  - Replicas may diverge; conflicts are resolved later (reconciliation, anti-entropy, CRDTs, etc.).
- Properties:
  - Always return responses while nodes are up, even if not fully up to date.
  - Consistency is weaker (eventual consistency, causal consistency, bounded staleness, etc.).

Examples (again, categories):

- Dynamo-style key–value stores (Dynamo, Riak, Cassandra, many DynamoDB configurations).
- Systems that allow multi-master writes and background conflict resolution.

## 6. CAP vs ACID and BASE

### 6.1 ACID vs CAP’s “C”

- **ACID (Atomicity, Consistency, Isolation, Durability)** refers to **transactions within a database**.
- ACID’s **Consistency** is about preserving **application invariants** across transactions (e.g., foreign keys, balance ≥ 0).
- CAP’s **Consistency** is about **linearizable behavior of a distributed object across nodes**.

A system can be **ACID inside each shard** and still behave in different CAP modes when replicating or distributing those shards.

### 6.2 BASE

- **BASE** = Basically Available, Soft state, Eventually consistent.
- Not a theorem, but a design style for AP-oriented systems:
  - **Basically Available**: the system aims to answer queries even during failures.
  - **Soft state**: state may change even without new input (due to replication/reconciliation).
  - **Eventually consistent**: replicas converge if no new updates arrive.

BASE reflects design choices made because of CAP constraints, particularly in AP systems.

---

## 7. Using CAP in System Design

When designing or reviewing a system:

1. **Assume partitions can happen.**  
   Treat P as given for any non-trivial distributed deployment.

2. **Identify data that must be linearizable.**  
   Money balances, uniqueness constraints, critical configuration.  
   Design **CP-like subsystems**: leader/majority, fail-fast under partitions.

3. **Identify data that can tolerate staleness.**  
   Social feeds, metrics, recommendations, caches.  
   Design **AP-like subsystems**: allow divergent replicas, reconcile later.

4. **Use tunable consistency.**  
   Many systems let you trade off C vs A per operation (e.g., quorum settings for reads/writes).

5. **Document behavior under partition explicitly.**  
   Decide upfront what happens when nodes cannot reach each other: errors vs stale reads vs queued writes.

CAP does not forbid strong consistency or high availability; it forces you to **choose what to sacrifice during partitions**.
