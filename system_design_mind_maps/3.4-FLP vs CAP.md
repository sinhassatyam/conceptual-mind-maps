# FLP vs CAP — Relationship, Differences, and Related Concepts

> Based on: Henry Robinson’s CAP FAQ and FLP write-ups, Gilbert–Lynch CAP proof, and standard FLP/CAP literature.

---

## 1. High-Level View

Both **FLP** and **CAP** are classic **impossibility results** in distributed systems, but they address **different problems** under **different assumptions**:

- **FLP (Fischer–Lynch–Paterson)**  
  Impossibility of deterministic **consensus** in a fully asynchronous system with even one possible crash failure and no message loss.

- **CAP (Brewer / Gilbert–Lynch)**  
  Impossibility of building an **atomic, always-available, partition-tolerant read/write store** in an asynchronous system with possible message loss (partitions).

They share themes (asynchrony, safety vs liveness) but are not the same theorem and do not reduce to each other.

---

## 2. Core Differences

### 2.1 Problem Being Solved

- **FLP**
  - Target: **consensus** — all processes must agree on a single value.
  - Requirements: Termination, Agreement, Validity.
  - Output: Each correct process eventually decides one value.

- **CAP**
  - Target: **distributed read/write register** (or key–value store).
  - Requirements: Atomic (linearizable) consistency, Availability, Partition tolerance.
  - Output: Clients perform repeated reads/writes on shared state.

Consensus is a *building block* for many systems. CAP is about the observable behavior of storage under network partitions.

### 2.2 Failure Model and Network Behavior

- **FLP model**
  - Fully asynchronous timing: unbounded delays.
  - At most one process may **crash**.
  - Messages are **never lost**, only arbitrarily delayed.
  - Crashed processes do not have to decide.

- **CAP model**
  - Asynchronous timing: unbounded delays.
  - Nodes are assumed reliable in the proof; the key failure is **message loss** due to partitions.
  - During a partition, messages between some subsets of nodes are dropped indefinitely.
  - Nodes in any partition are still expected to respond to client requests.

This difference is crucial:

- In FLP, a completely partitioned-off process can be treated as crashed and exempt from deciding.
- In CAP, partitioned nodes must still answer requests correctly if the system claims both C and A.

### 2.3 What is Impossible?

- **FLP**
  - No deterministic algorithm can guarantee **termination of consensus** in all admissible runs.
  - Safety (agreement, validity) can be preserved; liveness (termination) fails in some runs.

- **CAP**
  - No distributed register can be **both atomic and always-available** under all partition scenarios.
  - Safety (atomicity) or liveness (availability) must be sacrificed during partitions.

In both cases, the impossibility targets **liveness** under certain failure and timing conditions.

---

## 3. How They Interact Conceptually

Conceptually:

- FLP constrains the design of **coordination / consensus protocols**.
- CAP constrains the design of **data stores / replicated objects** under partitions.

Even if you had a hypothetical consensus algorithm that somehow “beat” FLP (always terminates in a fully asynchronous, crash-prone system), that would not automatically solve CAP, because:

- CAP requires that **every node participating in a partition** respond to client operations in a way that maintains atomicity and availability.
- A consensus protocol typically focuses on getting *nodes* to agree; CAP is about **clients’ read/write operations** on replicated state in the face of connectivity loss.

## 4. When to Use FLP vs CAP Thinking

### 4.1 Think FLP When…

You are designing or reasoning about **agreement / coordination mechanisms**:

- Leader election.
- Cluster membership.
- Global configuration changes.
- Replicated log (e.g., Raft/Paxos/Zab).

Questions you ask:

- “Can all correct nodes always agree on this value?”
- “Under what timing/failure conditions might progress stall?”

FLP reminds you that in pure asynchrony, deterministic consensus algorithms **may never terminate** in some executions, so real systems rely on additional assumptions like partial synchrony or failure detectors.

### 4.2 Think CAP When…

You are designing or reasoning about **replicated data services**:

- Key–value stores.
- Document databases.
- Sharded and replicated RDBMS deployments.

Questions you ask:

- “How will the system behave when the network splits?”
- “Will I return stale data, or will I refuse/queue requests?”
- “Which data must be strongly consistent vs eventually consistent?”

CAP reminds you that under partitions, you must choose between **CP** (sacrifice availability) and **AP** (sacrifice strong consistency) behaviors.

## 5. Related Concepts and How They Differ

### 5.1 Partial Synchrony

- Model where the system is asynchronous for some time but eventually becomes synchronous (bounded delays).
- Many consensus protocols (Paxos, Raft) are proven correct in partially synchronous models.
- Differs from FLP:
  - FLP assumes **pure asynchrony** forever; partial synchrony relaxes this, making deterministic consensus attainable after some unknown stabilization time.

### 5.2 Failure Detectors

- Abstract oracles that give hints about failed processes (e.g., “suspect(process X)”).
- Chandra & Toueg showed consensus can be solved in asynchronous systems with appropriate failure detectors.
- Differs from FLP:
  - FLP assumes **no failure detector**, making processes unable to distinguish slow from failed nodes.

### 5.3 Consistency Models Beyond Linearizability

- **Sequential consistency**: all processes see operations in the same order, but it doesn’t have to match real-time order.
- **Causal consistency**: preserves causal (happens-before) relationships but not a total order.
- **Eventual consistency**: if no new updates occur, all replicas eventually converge.

Relation to CAP:

- CAP’s “C” is specifically **linearizability (atomicity)**.
- Weaker models are often adopted in AP systems to improve availability and performance at the expense of strong C.

### 5.4 ACID vs CAP vs BASE

- **ACID**: properties of local database transactions; its “Consistency” means preserving invariants.
- **CAP**: trade-off between linearizable consistency and availability under partitions in distributed systems.
- **BASE**: design style for AP systems (Basically Available, Soft state, Eventually consistent), reflecting a bias toward availability and partition tolerance.

They operate at different layers but interact in real designs.

### 5.5 Consensus Protocols (Paxos, Raft, Zab)

- Concrete algorithms for achieving consensus despite failures.
- Respect FLP by:
  - Guaranteeing safety (no diverging decisions) even under asynchrony.
  - Guaranteeing liveness only under additional assumptions (partial synchrony, eventually timely networks).

They are often used as the core of **CP systems** in the CAP sense.

---

## 6. Design Takeaways

- **From FLP**:
  - In a fully asynchronous system with crash failures, you cannot guarantee that deterministic consensus always terminates.
  - Practical consensus systems accept that under extreme conditions, they might stall to protect safety.

- **From CAP**:
  - In a system that can partition, you cannot guarantee both linearizable consistency and full availability.
  - Practical data stores choose CP or AP behavior (often tunable) for different data types and operations.

When designing distributed systems:

1. Use **FLP** to reason about limits and assumptions for your **coordination/consensus layer** (e.g., leader election, configuration).
2. Use **CAP** to reason about behavior of your **data layer** under partitions (CP vs AP trade-offs).
3. Use **partial synchrony, failure detectors, and weaker consistency models** as tools to move from theoretical impossibility to practical systems that work well in the common case.
