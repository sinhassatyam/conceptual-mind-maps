## Module 1 – Core Philosophy & Evolution
### 1.1 Genesis: why dedicated load balancers appeared
Early web stacks were:

- One or a few big web servers (Apache, IIS) on a single box.
- Vertical scaling (bigger box) as the primary knob.

Bottlenecks that forced dedicated LBs into existence:

- **Single‑host limits**
  - File descriptor limits (`ulimit`), kernel connection tables, NIC PPS limits.
  - Per‑process threading overhead in “1 thread per connection” designs.
- **Scaling “by hand”**
  - Adding more web servers required:
    - Manual DNS juggling.
    - Manual firewall/NAT rules.
    - Inconsistent operational patterns across apps.
- **High‑availability gaps**
  - No clean way to:
    - Take a node out of rotation gracefully.
    - Fail over on node/DC failure without clients noticing.

Vendors introduced **hardware load balancers** to centralize:

- Connection acceptance.
- Distribution logic.
- Health checking and failover.
- Policy enforcement (SSL termination, security features).

Later, **software LBs** like HAProxy and NGINX emerged as lightweight, commodity alternatives. [docs.haproxy](https://docs.haproxy.org/1.7/management.html)
### 1.2 Problems uniquely solved vs alternatives
1. **DNS round‑robin**
   - Multiple A records for one hostname.  
   - Problems:
     - **Client‑side caching**: resolvers and browsers cache DNS responses, ignore low TTLs.
     - **No health awareness**: if one IP is dead, clients still try it until cache flush.
     - **Coarse granularity**: no per‑request rebalancing, only per‑lookup.
2. **Client‑side load balancing**
   - Clients embed list of servers and choose (random, round‑robin).
   - Problems:
     - Every client needs **service discovery and health logic**.
     - Hard to change server list quickly (mobile apps, IoT).
     - Fragmented behavior; no central view or control.
3. **Single big box / vertical scaling**
   - Bigger VM/bare metal.
   - Problems:
     - Hard physical limit on CPU/RAM/NIC bandwidth.
     - Single point of failure.
     - Poor cost scaling; upgrades are lumpy events.
4. **Static L3 routing tricks**
   - Using static routes or ECMP/OSPF to spray traffic.
   - Problems:
     - No application‑level awareness (HTTP codes, timers).
     - No session stickiness.

Dedicated L4/L7 LBs solve:

- Centralized **policy + health**.
- Fine‑grained **per‑connection/request** distribution.
- **Rolling upgrades and blue‑green** without client changes.
- Decoupling of **service IP/DNS identity** from underlying mutable compute.
### 1.3 The state problem: decoupling state from compute
State challenges:

- TCP state lives in kernel conntrack.
- Application session state often lives in process memory.

L4 LBs decouple:

- **Network state**: the LB owns the public “service IP”, sees full 4‑tuple / 5‑tuple flows.
- Backend pool becomes a **set of ephemeral workers**; LB steers flows while tracking connection state.
- Backends can fail/scale without changing the external IP or DNS.

L7 LBs further decouple:

- **Application state**: by terminating HTTP/TLS, they:
  - Can implement **stickiness** at HTTP cookie level.
  - Can hide backend restarts by retrying requests, transforming errors, etc.
- Combined with external data stores (Redis, DB), they allow **stateless app servers**.

Result: high availability comes from **moving state to shared infrastructure** and using LBs as the indirection layer between client identity and mutable backend fleet.

## Module 2 – Layer‑4 Load Balancer Architecture
### 2.1 Packet‑level flow through an L4 LB
Consider a TCP‑based L4 LB in front of HTTP servers, in **NAT mode**.

1. **Client initiates**
   - Client sends `SYN` to `VIP:80` (VIP = LB’s virtual IP).
   - Packet fields:
     - `src_ip = client_ip`
     - `src_port = cport`
     - `dst_ip = vip`
     - `dst_port = 80`
2. **LB receives SYN**
   - LB examines 4‑tuple or 5‑tuple: `(src_ip, src_port, dst_ip, dst_port, protocol)`.
   - Chooses backend according to hash/algorithm.
   - Installs **connection tracking entry**:
     - Maps `(client_ip, cport, vip, 80)` → `(backend_ip, bport)` with current TCP state (SYN‑RECEIVED, etc.).
3. **LB forwards SYN to backend**
   - In NAT mode:
     - LB rewrites:
       - `dst_ip = backend_ip`
       - `dst_port = backend_port` (usually 80 or internal port).
       - Optionally `src_ip` to LB local IP (SNAT).
   - Sends `SYN` to backend.
4. **Backend replies SYN‑ACK**
   - Backend responds to LB’s source:
     - `src_ip = backend_ip`
     - `dst_ip = lb_ip` (or vip)
     - `flags = SYN, ACK`
   - LB looks up conntrack entry, rewrites back to client:
     - `src_ip = vip`
     - `dst_ip = client_ip`
     - Preserves TCP seq/ack.
5. **ACK completes handshake**
   - Client sends `ACK` to `vip`.
   - LB maps to backend and forwards.
   - TCP state in LB moves to ESTABLISHED.
6. **Data transfer**
   - All subsequent packets:
     - Client → VIP: LB → backend.
     - Backend → LB → client.
   - LB only touches headers; payload can be forwarded with minimal copying.
7. **FIN/RST and teardown**
   - When either side closes:
     - LB updates conntrack state (FIN‑WAIT, TIME‑WAIT, etc.).
     - Eventually removes entry after timeout.

Data path: no parsing of HTTP; only transport‑layer fields matter.
### 2.2 Packet routing modes: NAT, DSR/DR, IP Tunneling
#### 2.2.1 NAT mode (SNAT/DNAT)

- **Topology**
  - Clients send to VIP (on LB).
  - Backends are in private subnet or same L2 segment.
- **Header mutations**
  - DNAT: `VIP:port → backend_ip:port` (dest IP/port changed).
  - SNAT: LB may change source IP to its own IP for backend responses.
- **Return path**
  - All return traffic flows back through LB (symmetric).
- **Pros**
  - Simple deployment; no special host config.
  - Works across subnets/VLANs.
- **Cons**
  - LB must process **both directions** of traffic → more CPU and NIC bandwidth.
  - Conntrack table holds full duplex flow entries.

#### 2.2.2 DSR / DR (Direct Server Return)

- **Idea**
  - LB only handles **incoming** traffic; responses go **directly** back to client.
- **Topology**
  - VIP is configured on LB and **loopback interface** of each backend (non‑ARPing / `arp_ignore/arp_announce` tweaks).
  - All machines on same L2 segment.
- **Flow**
  - Client SYN → VIP MAC (LB’s MAC) → LB.
  - LB **only rewrites MAC dest** to backend’s MAC (no IP change).
  - Backend sees `dst_ip = VIP` on a loopback alias; stack accepts it.
  - Backend responds directly:
    - `src_ip = VIP`, `dst_ip = client_ip`, L2: backend MAC → gateway / client.
- **Header mutations**
  - Only L2 MAC addresses change in LB; IP header untouched.
- **Pros**
  - LB offloads reply path → half the data path load.
  - High throughput, popular in old hardware LB designs.
- **Cons**
  - Requires:
    - L2 adjacency; doesn’t work across routed subnets.
    - Careful ARP config to avoid IP conflict.
  - No SNAT; client sees VIP as source IP.

#### 2.2.3 IP Tunneling (IP‑in‑IP / GRE)

- **Idea**
  - LB encapsulates client packet into a new IP header, tunnels to backend.
- **Flow**
  - Client → VIP (LB).
  - LB wraps original packet:
    - Outer header: `src_ip = lb_ip`, `dst_ip = backend_ip`.
    - Inner header: original `client_ip → vip`.
  - Backend decapsulates; sees inner packet as if sent directly.
  - Backend replies directly to client (if VIP configured on loopback) or via LB, depending on design.
- **Pros**
  - Works when LB & backend are not L2‑adjacent (cross‑DC).
  - Similar properties to DSR in terms of IP visibility.
- **Cons**
  - Encapsulation overhead:
    - MTU reduced; possible fragmentation.
    - Extra CPU for encapsulate/decapsulate.
  - Requires tunnel support on backends.
### 2.3 Session tracking & hashing
#### 2.3.1 Conntrack tables

An L4 LB must maintain **connection state**:

- Key: 5‑tuple `(src_ip, src_port, dst_ip, dst_port, protocol)`.
- Value:
  - Backend identity (server index/IP).
  - TCP state (SYN‑RECEIVED, ESTABLISHED, FIN‑WAIT, etc.).
  - Timers and idle time.

Conntrack is typically implemented as:

- Hash table with buckets:
  - `bucket_index = hash(5‑tuple) mod N`.
- Time‑wheel or heap for timeout management.

Memory and scaling:

- Each connection consumes a fixed struct (e.g., tens to hundreds of bytes).
- 1M connections → order of 100–200 MB state, plus overhead.
- Scaling strategies:
  - Shard across threads/cores.
  - Use RSS (Receive Side Scaling) NIC queues consistent with hash.

#### 2.3.2 Hashing: 2‑tuple, 3‑tuple, 5‑tuple

- **2‑tuple**: `(src_ip, dst_ip)`
  - Rough per‑client distribution; many flows from same client may be stuck to one backend.
- **3‑tuple**: `(src_ip, dst_ip, dst_port)`
  - Distinguishes multiple services per client.
- **5‑tuple**: adds `src_port` and `protocol`
  - More uniform distribution across high connection concurrency.
- **Consistent hashing**
  - Minimizes reassignment on backend add/remove.
  - Used when you want “user stickiness” without global rebalance.
  - Example: Google Maglev’s consistent hashing table to map flows to backends. [blog.acolyer](https://blog.acolyer.org/2016/03/21/maglev-a-fast-and-reliable-software-network-load-balancer/)

#### 2.3.3 TCP handshakes and auto‑scaling

- **Without consistent hashing**
  - If you change backend set (scale out/in), hash(client → backend) may change.
  - New connections from same client can land on different backends → fine for stateless L4.
- **With session persistence**
  - You can:
    - Use source IP consistent hashing to keep clients on same backend.
    - Accept some churn when scaling; old flows are tracked via conntrack until teardown.
  - High‑end L4 designs (Maglev, Hyperplane) use:
    - Deterministic consistent hashing with:
      - Shared lookup table across LB nodes.
      - Minimizing remaps when backends change. [ocheselandrei.github](https://ocheselandrei.github.io/2021/10/17/how-does-a-lb-scale.html)

Handling handshake:

- SYN arrives → choose backend and record mapping (conntrack).
- As backend set changes:
  - Existing connections continue using old mapping (stateful).
  - New connections use new mapping computed from updated backend set.
- LB must ensure **no race** during state updates:
  - Update backend list atomically.
  - Graceful draining for backends being removed.

## Module 3 – Layer‑7 Load Balancer Architecture
### 3.1 Internal working: two TCP connections
For HTTP/HTTPS:

1. **Client → LB connection (frontend)**
   - LB accepts TCP (or TLS) on `VIP:443`.
   - If TLS terminated:
     - LB performs handshake, validates SNI, picks cert/key.
   - LB reads HTTP request bytes into per‑connection buffer.

2. **LB → Backend connection (backend)**
   - LB either:
     - Opens new TCP connection per request (simple, higher overhead).
     - Or uses **connection pools**: persistent connections reused across multiple client requests.
   - LB writes parsed/request bytes to backend, possibly with:
     - Header rewriting (`Host`, `X-Forwarded-For`, etc.).
     - HTTP protocol downgrade/upgrade (e.g., 1.1 to 1.0).

3. **Response path**
   - Backend sends HTTP response.
   - LB reads, optionally transforms (compression, chunking), and pushes to client.

For HTTP/2 or HTTP/3:

- LB implements full protocol stack:
  - **HTTP/2**: frames, streams, flow control.
  - **HTTP/3**: QUIC over UDP, stream multiplexing, congestion control.
### 3.2 Parsing and buffering
#### 3.2.1 HTTP/1.1

- **Request line**: `METHOD SP URI SP HTTP/version CRLF`.
- **Headers**: key/value pairs terminated by `CRLF CRLF`.
- LB behavior:
  - Reads bytes from socket into buffer.
  - Parses request line + headers; checks size limits: `client_header_buffer_size`, `large_client_header_buffers` (NGINX). [blog.nginx](https://blog.nginx.org/blog/inside-nginx-how-we-designed-for-performance-scale)
  - For large bodies:
    - Streams body in chunks from client to backend (no need for full buffering).
- **Chunked encoding**
  - LB must parse chunk sizes and boundaries:
    - `"size\r\n<data>\r\n"` repeated until `"0\r\n\r\n"`.
  - It may:
    - Pass chunks through unmodified.
    - Or normalize to a known format for backend.

#### 3.2.2 HTTP/2

- Binary framing:
  - Headers encoded as HPACK compressed header blocks.
  - Multiple **streams** multiplexed over one TCP connection.
- LB engine:
  - Maintains per‑stream state machine:
    - OPEN, HALF_CLOSED, CLOSED.
  - Flow control windows per stream + connection.
- Mapping streams:
  - LB may map each upstream HTTP/2 stream to:
    - Separate upstream HTTP/2 stream on pooled backend connection.
    - Or separate HTTP/1.1 requests on backend connections.

#### 3.2.3 HTTP/3 (QUIC)

- QUIC encapsulates:
  - Streams.
  - Flow control.
  - Retransmission at user‑space, over UDP.
- LB as HTTP/3 terminator:
  - Implements QUIC handshake (TLS 1.3 + transport).
  - Maintains per‑connection state: packet numbers, congestion window, ACK ranges.
- Typical cloud L7 LBs terminate HTTP/3 and speak HTTP/2 or HTTP/1 to backends to avoid pushing QUIC down into the application.
### 3.3 Advanced routing capabilities
#### 3.3.1 Path / Host / header routing

- **Path‑based**
  - Example: `/api/*` → API cluster; `/static/*` → static cluster.
  - Implementation:
    - Parse URI from request line.
    - Use routing tree / prefix match / regex engine.
- **Host‑based**
  - `Host: foo.example.com` → service A.
  - `Host: bar.example.com` → service B.
- **Header / cookie‑based**
  - `X-Canary: true` → canary backend.
  - Cookie value `(user_segment=beta)` → special cluster.

Internals:

- Many systems maintain:
  - A route table, often a tree (path segments) + maps for hosts.
  - Match chain: host → path → header/cookie rules.
- Implementation must be O(1) or O(log N) for route count; naive regex use is a common perf path.

#### 3.3.2 TLS termination vs passthrough vs re‑encryption

- **TLS termination**
  - LB accepts TLS, decrypts, sees HTTP.
  - Can:
    - Do full L7 routing.
    - Apply WAF, compression, caching.
  - Backend sees HTTP (or HTTPS from LB if re‑encrypting).
- **TLS passthrough**
  - LB just routes TCP segments based on L4 info:
    - No decryption.
    - No Host/path inspection.
  - Useful when:
    - End‑to‑end encryption mandated.
    - App uses non‑HTTP TLS protocols.
- **TLS re‑encryption**
  - LB terminates client TLS, then opens TLS to backend.
  - Pros:
    - End‑to‑end encryption.
    - L7 features at LB.
  - Cons:
    - Double crypto overhead.

**SNI parsing**

- Even without decrypting, LBs can inspect SNI (Server Name Indication) in TLS ClientHello:
  - Route `foo.example.com` vs `bar.example.com` to different backends.
- For HTTP/2+TLS, SNI + ALPN decide which protocol to speak.

**Session tickets/resumption**

- LB managing TLS sessions:
  - Retains session tickets or session IDs to accelerate resumption.
  - In multi‑LB setups:
    - Needs ticket key sharing or external session store; otherwise resumption only works when client hits same LB.

#### 3.3.3 Sticky sessions (L7)

- **Injected cookie**
  - LB sets cookie: `Set-Cookie: LBID=backendX; Path=/`.
  - On future requests, LB reads `LBID` and sends request to same backend.
- **Application cookies**
  - LB uses existing cookies (e.g., `JSESSIONID`) as stickiness key:
    - Hash(cookie value) → backend index.
- Typically implemented using:
  - **Stick tables** (HAProxy).
  - Shared in‑memory maps keyed by IP/cookie.

## Module 4 – Infrastructure & Highly Available Topology
### 4.1 Control plane vs data plane
- **Data plane**
  - Actual packet processing and request handling.
  - In HAProxy/NGINX:
    - Worker processes using epoll/kqueue event loops, tight loops in C. [docs.haproxy](https://docs.haproxy.org/1.7/management.html)
  - In cloud LBs:
    - Kernel bypass / DPDK / eBPF/XDP for L4.
    - Proxy fleet (Envoy/NGINX) for L7.
- **Control plane**
  - Configuration, discovery, health data, policy.
  - Responsibilities:
    - Push backend membership / configs.
    - Distribute TLS certificates and rotation.
    - Manage LB fleet membership (autoscaling, cell boundaries).

Separation:

- Data plane must be **fast and predictable**; control plane can be eventually consistent but must not block data path.
- Changes in control plane produce atomic, low‑latency updates to in‑memory structures in workers.
### 4.2 Active‑passive vs active‑active
#### 4.2.1 Active‑passive + VRRP

- VRRP (Virtual Router Redundancy Protocol):
  - Multiple routers share a virtual IP (VIP).
  - One acts as **MASTER**, others as **BACKUP**.
- Mechanics:
  - MASTER sends VRRP advertisements periodically.
  - If BACKUP doesn’t see them for `N` intervals, it assumes master is dead and **claims VIP**:
    - Sends gratuitous ARP; upstreams update ARP cache to point to new MAC.
- In LB context:
  - Two HAProxy/NGINX nodes; shared VIP.
  - Pros:
    - Simple to reason about.
  - Cons:
    - Only one node used for traffic.
    - Failover still costs some seconds depending on timers and ARP caching.

#### 4.2.2 Active‑active + BGP Anycast + ECMP

- **Anycast VIP**
  - Same IP prefix announced from multiple LB nodes/PoPs via BGP.
- **Routers with ECMP**
  - Treat multiple LB nodes as equal‑cost next hops.
  - Distribute flows based on hash (5‑tuple) across LB nodes. [ocheselandrei.github](https://ocheselandrei.github.io/2021/10/17/how-does-a-lb-scale.html)
- Properties:
  - Horizontal scaling: add LB nodes, announce prefix, routers share load.
  - Failure handling:
    - Failing LB withdraws its route → traffic rehashed across remaining nodes.
- Used by:
  - Google Maglev. [sre](https://sre.google/workbook/managing-load/)
  - Cloud NLBs (AWS Hyperplane uses BGP/ECMP internally). [ocheselandrei.github](https://ocheselandrei.github.io/2021/10/17/how-does-a-lb-scale.html)
- Challenges:
  - Keeping hashing tables consistent across all LB nodes (for stickiness).
  - Handling stateful flows during node failures.
### 4.3 Health checking architecture
- **Active checks**
  - Dedicated threads or workers periodically send probes:
    - TCP connect, HTTP GET/HEAD, gRPC health, custom scripts.
  - Results are aggregated and stored in:
    - Shared memory or distributed store.
- **Passive checks**
  - Data plane inspects actual traffic:
    - Track HTTP 5xx from backend.
    - Track TCP errors/timeouts.
  - Mark backend as suspect if thresholds exceeded.

**Flap damping**

- If a backend flips between UP/DOWN rapidly:
  - Put it into “quarantine” or degraded state for some time.
  - Hysteresis in state transitions:
    - Require `n` consecutive successes to mark UP.
    - Require `m` consecutive failures to mark DOWN.
- Prevents “thundering herds” and routing instability.

### 5.2 HAProxy
- **Internal engine**
  - Multi‑threaded, event‑driven, non‑blocking I/O using epoll/kqueue. [docs.haproxy](https://docs.haproxy.org/1.7/management.html)
  - Single process with multiple worker threads; often one per CPU.
- **Strengths**
  - Very efficient L4 proxy, capable of hundreds of thousands of connections per instance.
  - Rich L7 HTTP features (ACLs, header manipulation, stick tables).
  - Dynamic reconfiguration via runtime API/UNIX socket.
- **Scalability bottlenecks**
  - Ultimately limited by:
    - Single machine NIC bandwidth, CPU cycles, FD limits.
    - Kernel networking overhead (unless using eBPF/DPDK frontends).
- **Unique features**
  - Stick tables for tracking per‑key (IP/cookie) state (rate limiting, abuse detection).
  - Advanced ACL language and routing rules.
### 5.3 NGINX
- **Internal engine**
  - Master process:
    - Loads config, binds ports, spawns workers.
  - Worker processes:
    - Single‑threaded event loops using epoll/kqueue. [blog.nginx](https://blog.nginx.org/blog/inside-nginx-how-we-designed-for-performance-scale)
    - Handle accept, read, write, parse, and upstream communication.
- **Strengths**
  - Combines **web server** and **reverse proxy** roles.
  - Extremely low per‑connection overhead:
    - Efficient memory pools and buffer reuse. [mohitmishra786.github](https://mohitmishra786.github.io/chessman/2024/12/29/Understanding-NGINX-Worker-Architecture.html)
- **Scalability limits**
  - Per‑worker limit: open FDs and CPU per core.
  - OS and NIC constraints still apply.
- **Unique features**
  - NGINX Plus: dynamic upstreams, active health checks, REST API.
  - Strong ecosystem (ingress controller, service mesh sidecar variants).
### 5.4 AWS ELB / NLB / ALB
- **Classic ELB**
  - Early generation multi‑tenant LB:
    - TCP/SSL + HTTP/HTTPS listeners, health checks, stickiness. [docs.aws.amazon](https://docs.aws.amazon.com/elasticloadbalancing/latest/classic/elb-add-or-delete-listeners.html)
  - Internally a fleet of proxies + AWS network virtualization.
- **NLB (Hyperplane)**
  - L4 load balancer optimized for millions of concurrent connections and very high CPS. [ocheselandrei.github](https://ocheselandrei.github.io/2021/10/17/how-does-a-lb-scale.html)
  - Architecture (from public sources):
    - Cell‑based fleet; each cell handles subset of VIPs.
    - Uses BGP + ECMP to spread traffic across LB nodes. [ocheselandrei.github](https://ocheselandrei.github.io/2021/10/17/how-does-a-lb-scale.html)
    - Leveraging kernel‑bypass techniques for L4 for performance.
  - Features:
    - Static IP addresses per AZ.
    - Connection preservation; source IP preserved.
- **ALB**
  - L7 HTTP/HTTPS LB:
    - Path/host‑based routing.
    - WebSockets, HTTP/2, gRPC.
  - Multi‑tenant proxy fleet; integration with target groups, auto scaling.

Limits and constraints:

- Limits are adjustable per account/region, but practically:
  - NLB: very high PPS/CPS, but backend health config and target registration propagate via control plane (non‑instant).
  - ALB: more CPU heavy; heavy use of complex rules/regex increases latency.
### 5.5 Google Cloud Load Balancing / Maglev
- **Maglev**
  - Google’s proprietary distributed L4 LB. [sre](https://sre.google/workbook/managing-load/)
  - Nodes run in each cluster, BGP‑speaking, use:
    - ECMP from upstream routers to distribute flows.
    - Consistent hashing table (“Maglev hash”) to map flows to backends. [blog.acolyer](https://blog.acolyer.org/2016/03/21/maglev-a-fast-and-reliable-software-network-load-balancer/)
  - Packet‑level L4; very high throughput.
- **Google HTTP(S) Load Balancing**
  - Global L7 LB:
    - Single anycast IP worldwide.
    - Frontend proxies terminate HTTP(S), route to backend services/NEG.
  - Tight integration with Google’s SDN, firewall, and autoscaler.
### 5.6 Azure Load Balancer (Ananta)
- **Ananta architecture**
  - Scale‑out software L4 LB and NAT optimized for multi‑tenant cloud. [conferences.sigcomm](https://conferences.sigcomm.org/sigcomm/2013/papers/sigcomm/p207.pdf)
  - Uses:
    - A virtualized, distributed load‑balancing fabric.
    - Host agents on hypervisors + centralized controllers.
- **Features**
  - L4 load balancing for VMs and services.
  - Integration with Azure SDN for virtual networks.
- **Constraints**
  - Similar to other SDN‑based LBs:
    - Hard limits governed by per‑host forwarding capacity and control‑plane convergence.

## Module 6 – Production Configuration & Architectural Trade‑offs
### 6.1 L4 vs L7 comparison
| Aspect              | L4 LB                                              | L7 LB                                                     |
|---------------------|----------------------------------------------------|-----------------------------------------------------------|
| OSI Layer           | Transport (TCP/UDP)                                | Application (HTTP, gRPC, etc.) [a10networks](https://www.a10networks.com/glossary/how-do-layer-4-and-layer-7-load-balancing-differ/)                  |
| Data visibility     | IPs, ports, flags                                  | Methods, paths, headers, cookies, bodies [a10networks](https://www.a10networks.com/glossary/how-do-layer-4-and-layer-7-load-balancing-differ/)        |
| Performance         | Higher throughput, lower latency (less work) [a10networks](https://www.a10networks.com/glossary/how-do-layer-4-and-layer-7-load-balancing-differ/) | Lower throughput, higher per‑req CPU due to parsing [a10networks](https://www.a10networks.com/glossary/how-do-layer-4-and-layer-7-load-balancing-differ/) |
| CPU/RAM             | Lower per connection                               | Higher (protocol parsing, buffering)                     |
| Security features   | Basic: simple ACLs, rate limiting                  | WAF, auth, header‑based policies                         |
| Protocol awareness  | None (payload opaque)                              | Full (HTTP/2, WebSockets, etc.)                          |
| Operational complexity | Lower (simpler policies)                        | Higher (routing rules, version negotiation)              |
| DDoS handling       | Good for volumetric mitigation                     | Better for application‑layer attacks with WAF            |
| Use cases           | Generic TCP/UDP, databases, message queues         | Web APIs, microservices, multi‑tenant HTTP frontends     |
### 6.2 Config considerations (production hardening)
Key knobs for HAProxy/NGINX/LBs:

- **Timeouts**
  - `client_body_timeout`, `client_header_timeout`, `keepalive_timeout` (NGINX).
  - `timeout connect`, `timeout client`, `timeout server` (HAProxy).
  - Too low → spurious disconnects; too high → resource hogs.
- **Buffer sizes**
  - Socket buffers (sysctls `net.core.rmem_max`, `net.core.wmem_max`).
  - Per‑connection buffers; must balance memory vs throughput.
- **Connection pooling**
  - Upstream keep‑alive pool sizes.
  - Max concurrent upstream connections; protect DBs and services from thundering herds.
- **Ephemeral port exhaustion**
  - Many outbound connections from LB to same backend IP:port can hit ephemeral port limit (~64k).
  - Mitigations:
    - Use connection pooling and keep‑alive.
    - Use multiple backend IPs or ports.
    - Tune `net.ipv4.ip_local_port_range`.
- **Kernel tuning**
  - `somaxconn`, `tcp_max_syn_backlog`, `tcp_syn_retries`, `tcp_fin_timeout`.
  - RSS and IRQ affinity for NICs; pin LB workers to CPUs.
- **Zero‑copy optimization**
  - Use `sendfile()` or `splice()` to send data from disk to socket without copying via user‑space. [blog.nginx](https://blog.nginx.org/blog/inside-nginx-how-we-designed-for-performance-scale)
  - Reduces CPU load and memory bandwidth consumption.
  - Beware interaction with TLS (traditional sendfile cannot work on encrypted streams unless TLS offload supports it).
### 6.3 Identifying and debugging limits
1. **NIC throughput**
   - Check:
     - `ethtool` stats (drops, errors).
     - `sar`, `nload`, host metrics.
   - 10G/25G/100G line rate: track PPS and bytes.
2. **CPU saturation**
   - High sys% or softirq% suggests kernel networking bottlenecks.
   - Profile LB processes to find heavy parsing or regex.
3. **File descriptors**
   - `ulimit -n` must be high enough (e.g., 100k+).
   - Monitor per‑process FD usage.
4. **Context switching**
   - Too many worker processes, or per‑connection threads → context switch storm.
   - Event‑driven models (HAProxy/NGINX) minimize this by design. [blog.nginx](https://blog.nginx.org/blog/inside-nginx-how-we-designed-for-performance-scale)
5. **Conntrack table limits**
   - Linux conntrack size (`nf_conntrack_max`) must be tuned.
   - When full, new connections drop or bypass LB tracking.
6. **Latency spikes**
   - Correlate with:
     - GC pauses in control plane.
     - Config reloads (careful: NGINX supports zero‑downtime reload but misconfig can cause brief stalls).
     - Backend saturation causing head‑of‑line blocking in LB.
