# CAP, FLP, and Distributed Consistency — Deep Dive

> Synthesized from Henry Robinson’s CAP FAQ, his FLP articles, your CAP.md, and standard texts like *Designing Data-Intensive Applications* and Alex Xu’s *System Design Interview*. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

***

## 1. Big Picture: Why CAP and FLP Matter

Distributed systems have two fundamental pain points:

- **Agreeing on a single value or order of operations** across multiple nodes (consensus).
- **Serving reads/writes correctly and reliably** even when the network misbehaves.

Two classic impossibility results constrain what’s achievable:

- **FLP (Fischer–Lynch–Paterson, 1985):** In a fully asynchronous system, no deterministic algorithm can guarantee consensus terminates if even one node can fail. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)
- **CAP (Brewer conjecture, Gilbert & Lynch proof, 2002):** In an asynchronous system with possible message loss (partitions), you cannot have a read/write store that is always:
  - **C**: linearizable (atomic) consistency  
  - **A**: always available  
  - **P**: tolerant to partitions [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

Both are impossibility results; they don’t tell you how to build systems, they tell you **what you must give up or weaken**.

## 2. Core Definitions

### 2.1 System Model Basics

Common assumptions used in FLP and CAP proofs: [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- **Asynchronous network**
  - No upper bound on message delays.
  - Cannot distinguish a slow node from a failed node.
- **Processes / nodes**
  - Each runs some distributed algorithm.
  - Can fail in certain ways (fail-stop in FLP; CAP assumes no node failures but allows message loss).
- **Messages**
  - FLP: messages may be arbitrarily delayed but are not lost.
  - CAP: messages can be dropped (partitions).

These are intentionally pessimistic to produce strong impossibility statements.

### 2.2 Consensus (for FLP)

Consensus problem: Given processes each proposing a value, design an algorithm so that: [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

- **Termination:** Every non-faulty process eventually decides.
- **Agreement:** No two correct processes decide on different values.
- **Validity:** The decided value must be one of the proposed values.

FLP shows: **there is no algorithm that always satisfies all three in the asynchronous, crash-failure model**. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

### 2.3 Atomic / Linearizable Register (for CAP)

CAP formalizes an **atomic read/write register**: [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- Operations:
  - `set(X)` (write)
  - `get()` (read)
- **Atomic (linearizable) consistency:**
  - All operations appear as if executed on a single machine, in some global order consistent with real time. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
  - If A’s write completes before B’s read starts, B must see A’s write.

Atomic consistency is stronger than eventual consistency.

## 3. FLP Impossibility Theorem

### 3.1 Statement and Intuition

**FLP theorem:** In a fully asynchronous network with reliable delivery and possible crash of just one process, there is **no deterministic consensus algorithm** that is guaranteed to terminate in all admissible executions. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

Intuition:

- With unbounded message delays, a process cannot tell if another process crashed or is just slow.
- An adversarial scheduler can always delay some message at the “right” time to keep the system undecided (bivalent).
- Therefore, there exists at least one legal execution where the algorithm never terminates.

### 3.2 Key Concepts in the FLP Proof

Robinson’s “Brief Tour of FLP” walks through the original proof structure: [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

- **Configuration:** Full system state = local state of all processes + message buffer.
- **Event:** Delivery of a single message (or a special “no-op” delivery).
- **Run / schedule:** Sequence of events leading through configurations.

Valency:

- **0-valent / 1-valent:** From this configuration, all admissible runs eventually decide 0 (or 1).
- **Bivalent:** There exist runs deciding 0 and runs deciding 1 from this configuration.

Two crucial lemmas: [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

1. **Existence of a bivalent initial configuration**
   - Not all initial states can be predetermined to always decide 0 or always 1.
   - By continuity arguments over configurations differing in only one process’s initial value, at least one initial state is bivalent.

2. **Preservation of bivalence**
   - Starting from a bivalent configuration and any pending event `e`, there is some finite sequence in which `e` is eventually delivered that leads to another bivalent configuration.
   - Informally: by delaying some message sufficiently, you can stay indecisive.

Combining them:

- Starting at a bivalent configuration, repeatedly choose events and delay them “just right” to keep the system bivalent forever.
- Result: An admissible run (all messages eventually delivered, at most one failure) where **no process ever decides**.
- Hence, no “totally correct” consensus algorithm exists in this model. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

### 3.3 Practical Interpretation

- FLP does **not** say consensus always fails; it says **there exists** at least one adversarial execution where it might not terminate. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)
- Real systems:
  - Add **randomization**, **timeouts**, or assume **partial synchrony** (eventual bounds on delay), breaking the pure FLP model.
  - Consensus algorithms like Paxos/Raft are practical because they “work with probability 1” in real networks, even though FLP still applies at the theoretical edge.

## 4. CAP Theorem

### 4.1 Origin and Formal Statement

- Brewer’s 2000 PODC keynote introduced the conjecture (“you can’t have C, A, and P”). [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
- Gilbert & Lynch gave the formal proof in 2002. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

Formal CAP statement (Gilbert–Lynch-style): [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

In an asynchronous network where **messages can be lost (partitions)**, it is impossible to implement a read/write register that is:

1. **Available** – every request (read or write) to a non-failed node eventually returns a successful response (not an error). [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
2. **Atomic (linearizable)** – operations behave as if running on a single node in real-time order. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
3. **Partition tolerant** – the system continues operation despite arbitrary message loss. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

When a partition occurs, you must sacrifice **either C or A**.

### 4.2 Key Definitions (CAP FAQ framing)

Robinson’s CAP FAQ clarifies the terms: [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- **Read–write storage / register:**  
  Conceptual register with `set(X)` and `get()`; a KV-store is a set of such registers. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- **Availability (A):**
  - Every request to a non-failed node returns a correct response in finite time (no “sorry, I’m down”). [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
  - There is no fixed latency bound, but eventually must respond.

- **Consistency (C) = atomic / linearizable:**
  - All operations appear as if executed sequentially on one node, in an order consistent with real-time. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
  - External communication consistency: if A reads X and tells B, B must not later read a different value that contradicts this causal knowledge. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- **Partition tolerance (P):**
  - The network is allowed to **drop messages** between nodes. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
  - Total partition: no messages delivered between two groups of nodes; Gilbert–Lynch proof uses this. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

### 4.3 Why CAP is True (Intuition)

Proof sketch from the FAQ: [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- Suppose the cluster splits into two groups `G1` and `G2` with a **permanent partition** (no messages cross).
- A client writes value `X` to a register via some node in `G2`.
- Later, a client sends a read to a node in `G1`.
- For **atomic consistency**, that read must reflect the write of `X`.
- But `G1` can never learn about `X` (no messages from `G2`).
- So `G1` has two options:
  - Return **stale value** (break consistency).
  - **Refuse or block** the read (break availability).
- Therefore, no algorithm can maintain both C and A under partition.

Result: **Possibility of partitions ⇒ not (C and A)**. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

## 5. CAP vs FLP — Similarities and Crucial Differences

Henry Robinson’s “FLP and CAP aren’t the same thing” explicitly analyzes the relationship. [youtube](https://www.youtube.com/watch?v=3xhHhaCFAZI)

### 5.1 Shared themes

- Both are **impossibility theorems** in distributed systems.
- Both assume **asynchronous** timing models.
- Both talk about **safety** (never returning wrong answers) and **liveness** (eventually making progress). [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

### 5.2 Core differences

1. **Failure model**
   - **FLP:**
     - Messages are **never lost**, only delayed arbitrarily. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)
     - At most **one process can crash** and then take no further steps. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)
     - That node is exempt from needing to decide.
   - **CAP:**
     - Nodes do **not fail** in the proof model; the impossibility arises purely from **message loss / partition**. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)
     - Any **live node must respond** to requests (no “I silently crashed” escape).

2. **Problem being solved**
   - **FLP:** Consensus – processes must agree on a single value; termination is the liveness condition. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)
   - **CAP:** Atomic read/write storage – operations on a shared register must appear sequential & must always respond. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

3. **Treatment of partitioned nodes**
   - In **FLP**, a node that is completely partitioned can be considered **failed** and doesn’t have to decide. [youtube](https://www.youtube.com/watch?v=3xhHhaCFAZI)
   - In **CAP**, a partitioned node is **still required to respond correctly** to client requests; it cannot opt out. [youtube](https://www.youtube.com/watch?v=3xhHhaCFAZI)

Robinson’s key insight: even a hypothetical “FLP-solver” (a magical consensus algorithm for the FLP model) **cannot fully solve CAP**, because CAP demands correct responses from nodes that are isolated from updates. [youtube](https://www.youtube.com/watch?v=3xhHhaCFAZI)

### 5.3 Strength of results

- FLP assumes **no message loss** and still proves consensus might never terminate → a **stronger impossibility**. [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)
- CAP allows **message loss**, making the environment harsher; the result is intuitively less surprising (“of course you can’t be perfectly consistent and available if messages can vanish”). [youtube](https://www.youtube.com/watch?v=3xhHhaCFAZI)

## 6. CAP in Practice: CP, AP, and the “CA” Misconception

### 6.1 The misleading “pick any two” triangle

The classic diagram shows C, A, P as three corners and suggests you “pick any two.” CAP FAQ warns this is misleading: [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- In any realistic distributed system, **partitions are possible** (hardware failures, routing bugs, misconfigurations).
- You **cannot choose to “not be P”**; P is an environmental fact, not a design option.
- More accurate:  
  **If your system may partition, you cannot provide both C and A in all executions.** [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

That means “CA systems” are only meaningful for **single-site, non-distributed** systems (no partitions).

### 6.2 CP and AP categories

Practical classification (used in your CAP.md and in the primer): [singlestore](https://www.singlestore.com/blog/database-sharding-vs-partitioning-whats-the-difference/)

- **CP (Consistent, Partition-tolerant)**
  - On partition, sacrifice availability.
  - Typical behavior: reject or block operations on minority side.
  - Examples (approximate):
    - HBase, ZooKeeper, many strongly consistent NewSQL stores.

- **AP (Available, Partition-tolerant)**
  - On partition, accept operations and return possibly stale or divergent views.
  - Later reconcile (eventual consistency).
  - Examples:
    - Dynamo-style systems (Cassandra, Riak, DynamoDB in many modes). [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

Reality: many systems provide **tunable consistency** (e.g., Cassandra’s QUORUM reads/writes move you along a spectrum).

### 6.3 C and A as spectrums, not switches

FAQ stresses that once we **weaken the strict definitions** of A and C, we leave CAP’s formal world and enter design space: [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- **Relaxed consistency**:
  - Eventual consistency, causal consistency, read-your-writes, etc.
- **Relaxed availability**:
  - System is mostly available, but under some conditions returns errors or times out.

Real systems “trade down” from perfect C or perfect A to get useful behavior, but CAP still frames the extremes.

## 7. FLP and CAP in System Design: How to Use Them

### 7.1 What these theorems do NOT say

- They **do not say** distributed systems are hopeless.
- They **do not require** you to always be AP or always be CP.
- They **do not prevent** strong consistency or high availability in the **common case**.

They say:

- There exist executions (with partitions or adversarial scheduling) where you **must** choose between C and A (CAP), or **might not terminate** (FLP).

### 7.2 Design patterns guided by CAP/FLP

From your system-design primer and typical literature: [exasol](https://www.exasol.com/glossary/in-memory-database-definition/)

- For **critical data** (money, inventory):
  - Use **CP-like** subsystems: leader-based replication, majority-quorum, fail fast on partition.
  - Architect assuming **some operations will be rejected or delayed** during partitions.

- For **soft-state data** (feeds, counts, analytics):
  - Use **AP-like** subsystems: multi-master updates, per-node local writes, async repair.
  - Embrace **eventual consistency** and conflict resolution.

- For **consensus-based components** (config stores, service discovery):
  - Use algorithms like **Paxos/Raft** in a **partially synchronous** model.
  - Accept that in some pathological network conditions, progress may stall but safety remains.

## 8. Related Concepts and Terms

Briefly tying CAP/FLP to neighboring ideas you’ll see in Alex Xu and DDIA.

### 8.1 ACID vs CAP

- **ACID (Atomicity, Consistency, Isolation, Durability):**
  - Transactional properties within a database (often single node or tightly replicated).
  - “Consistency” here is **application invariants**, not CAP’s linearizability. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

- **CAP:**
  - About **distributed read/write objects** under partitions.
  - C = linearizability, A = availability as defined above. [techtarget](https://www.techtarget.com/searchstorage/answer/What-is-the-difference-between-cache-memory-and-RAM-cache)

They address different layers but interact:

- A system can offer **ACID transactions** inside a single shard yet still be **AP** at higher level by replicating asynchronously.

### 8.2 BASE and eventual consistency

- **BASE:** Basically Available, Soft state, Eventually consistent.
  - Shorthand for AP-oriented systems that prefer availability and accept temporary inconsistency.

- **Eventual consistency:**
  - If no new updates occur, all replicas eventually converge to the same value.

CAP tells you **you must sometimes step away from atomic consistency**, leading to BASE-like behaviors.

### 8.3 Partial synchrony and failure detectors

Work after FLP shows how to escape its impossibility: [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

- **Partial synchrony:** System is asynchronous “for a while” but eventually behaves synchronously (bounded delays).
- **Failure detectors:** Oracles that give hints about which nodes failed (with some error models).

Many practical consensus protocols are proven correct in **partially synchronous models with specific failure detectors**, not in pure FLP’s world.

## 9. How to Think Like the Original Designers

When applying CAP/FLP in design interviews or real systems, emulate the mindset of Brewer, Gilbert, Lynch, Fischer, Lynch, Paterson, and modern system designers: [youtube](https://www.youtube.com/watch?v=xfIF_H1uLEg)

- Start from **assumptions**:
  - What are my timing guarantees?
  - What failures do I assume (crash, partitions, Byzantine)?
- Decide on **safety vs liveness** trade-offs:
  - It’s better to be “correct but sometimes unavailable” for some use cases.
  - Better to be “always available but occasionally inconsistent” for others.
- Accept that **no algorithm can defeat these theorems**; instead:
  - Narrow the model (partial synchrony, bounded partitions).
  - Weaken guarantees (eventual consistency, bounded staleness).
  - Decompose the system into **CP parts and AP parts** by data type.

## 10. Practical Checklist for System Design Problems

When you see consistency/availability tension in a design exercise, ask:

1. **What is the failure model?**
   - Can messages be lost (partitions)? Can nodes crash? How many?
2. **Where do I absolutely need linearizable behavior?**
   - E.g., uniqueness, money, locks, leader election.
3. **Where can I tolerate staleness or conflicts?**
   - E.g., timelines, likes, metrics, search indexes.
4. **Under partition, what will my system choose to sacrifice?**
   - Return errors / fail fast (CP), or accept writes and reconcile later (AP).
5. **What consensus-like components do I need, and in what model?**
   - Raft/Paxos for config, membership, metadata; accept that extreme cases may stall progress.
